1. Distributed memory and MPI

Lecture 09 · textbook 3.1 · about 5 minutes

MPI runs one program as several processes, each with its own private memory. Nothing is shared, so data only moves when one process sends a message and another receives it.

  • Shared memory versus distributed memory:
    • shared memory: all threads see the same variables (pthreads works this way)
    • distributed memory: each process has its own private memory, and processes talk over a network
    • MPI is built for distributed memory
    • The same MPI program also runs on one machine with several cores
    • MPI hides whether two processes share a machine or not
  • Why communication cost shapes everything:
    • Sending data over a network takes time, while threads share data almost instantly
    • So MPI pays off when each process computes for a long time between messages
    • It fits data-parallel problems, where every process does the same work on a different piece of data
    • Lecture 09's example is a render farm: each machine renders its own animation frame
  • MPI compared with pthreads (lecture 09):
    • pthreads: shared memory, works with threads, built for concurrency, so you do all the parallel computation work by hand
    • MPI: distributed memory, works with processes, designed with parallel computation in mind
  • SPMD:
    • SPMD (single program, multiple data): every process runs the same executable
    • Different processes do different things by branching on their rank
    • The classic shape is if (my_rank != 0) { send } else { receive }
    • The textbook (3.1.5) points to the if-else in the hello program as what makes it SPMD
  • The calls every MPI program uses:
    • MPI_Init(NULL, NULL): starts MPI, must come before any other MPI call
    • NULL, NULL is fine when the program does not use argc and argv
    • MPI_Comm_size(MPI_COMM_WORLD, &comm_sz): stores how many processes there are
    • MPI_Comm_rank(MPI_COMM_WORLD, &my_rank): stores which process this is, from 0 to comm_sz - 1
    • MPI_Finalize(): shuts MPI down, no MPI calls are allowed after it
  • Two words to know:
    • communicator: a group of processes that can send messages to each other
    • MPI_COMM_WORLD is the communicator holding every process that mpiexec started
    • rank: a process's number inside a communicator, like a process id that does not depend on the system
    • Lecture 09 compares a communicator to a radio channel that processes listen on
    • Several communicators let different groups talk without picking up each other's messages
  • Compile and run:
    • mpicc is a wrapper around the C compiler that adds the MPI library
    • mpiexec -n 4 ./prog starts 4 processes of prog
    • Write programs that work for any number of processes, because you do not know the number in advance
  • Naming rule from the textbook (3.1.2):
    • Everything MPI defines starts with MPI_
    • Function names and types have a capital letter right after the underscore
    • Constants and macros are all capitals, like MPI_COMM_WORLD
  • Input and output:
    • Most implementations let only rank 0 read from stdin
    • So rank 0 calls scanf, then sends the values to everyone else
    • Every process can write to stdout, but the order is nondeterministic and lines can interleave
    • nondeterministic: the result can differ from one run to the next
    • To get ordered output, have the other ranks send their text to rank 0, which prints in rank order
    • mpi_hello.c does exactly this
    • Debug prints should include the rank
  • Error codes:
    • Most MPI functions return an int, and MPI_SUCCESS means it worked
    • The course examples ignore the return values to keep code short

2. Reading MPI code

Built for the code questions on lectures 09 to 11 · about 5 minutes

Most MPI exam questions ask what a program prints or whether it hangs. One short routine answers nearly all of them: work out who runs which lines, then pair every send with a receive.

  • Why a routine helps:
    • Every code question is the same question in different clothes: what does each rank do, and do the messages line up?
    • Doing the same steps in the same order stops you from reading the code top to bottom as if one process ran it
  • Step 1, fix the number of processes:
    • Use the number in the question, or pick a small one like 3 or 4
    • Write down every rank: 0, 1, 2, and so on
    • If the question says "for any number of processes", check p = 1 and p = 2 as well
  • Step 2, split the code by rank:
    • Find every if (my_rank ...) and decide which ranks take each branch
    • Lines outside any branch run on every rank
    • On the code pages, picking a rank in the lens does this for you, so use it to check your own answer
  • Step 3, list the communication each rank makes:
    • For each rank, write its calls in order: Send to 0, tag 0 or Recv from 1, tag 0
    • Loops count: a loop for (q = 1; q < comm_sz; q++) on rank 0 is comm_sz - 1 calls
    • A collective is one call on every rank, so it goes on every rank's list
  • Step 4, match them up:
    • A send and a receive match when the communicator, the tag, the source and the destination all agree
    • The datatypes must agree too, and the receive count must be at least the send count
    • Collectives match by the order they are made, so check that every rank has the same sequence
    • Every send needs exactly one receive, and every receive needs exactly one send
    • Section 3, Send and receive, has a lab for this step
  • Step 5, ask whether anything waits forever:
    • A receive with no matching send waits forever
    • Two ranks that both do a blocking send first and then a receive can wait on each other
    • A collective that one rank skips leaves the others waiting
    • deadlock: a set of processes each waiting for something only another waiting process could provide
  • Step 6, predict the output:
    • Only print statements produce output, so find which ranks reach each printf
    • If just one rank prints, the order is fixed
    • If several ranks print, the order can change from run to run, so say "any order"
    • If rank 0 prints what it received in a loop, the order follows the loop (the source it asks for)
  • Try the routine on this program:
    • Step 2: rank 1 runs the send, rank 0 runs the receive, and any other rank runs nothing
    • Step 3: rank 1 has Send to 0, tag 5, rank 0 has Recv from 1, tag 7
    • Step 4: the source and destination agree, but the tags (5 and 7) do not
    • Step 5: rank 0 waits forever, so the program hangs
    • Hangs and mix-ups on the Code pages runs this exact program
  • Takeaway:
    • Split by rank, list each rank's calls, match them, then look for waits

3. Send and receive

Lecture 09 · textbook 3.1 · about 10 minutes

A message only arrives when a send and a receive agree on the communicator, the tag, and who is talking to whom. When they do not, the receiver waits forever.

  • Point-to-point communication: one process sends, exactly one process receives
    • The two functions are MPI_Send and MPI_Recv
  • MPI_Send:

    • Signature:

    • buf, count, datatype describe the data: where it is, how many elements, what type

    • count is a number of elements, not bytes
    • dest, tag, comm describe where it goes
    • tag is a non-negative int that lets a receiver tell kinds of messages apart
    • The textbook's example: tag 0 for messages to print, tag 1 for messages used in a computation
    • MPI_Send(greeting, strlen(greeting)+1, MPI_CHAR, 0, 0, MPI_COMM_WORLD) sends a string to rank 0
    • The +1 sends the terminating '\0' too
  • MPI_Recv:

    • Signature:

    • The first six arguments mirror MPI_Send

    • Here count is how many elements the buffer can hold, not how many arrived
    • status receives details about the message, or pass MPI_STATUS_IGNORE
    • The receiver must already know the type, and an upper limit on the size
  • Message matching:
    • A send from process q to process r is received by r's MPI_Recv when all of these hold
    • Both use the same communicator
    • The tags are equal
    • r's source is q, and q's dest is r
    • The buffers are compatible: same datatype, and the receive count is at least the send count (the textbook's rule of thumb)
  • Try the matching rules:
    • Change one thing at a time and see which check fails
    • The presets reproduce programs in examples/extras/

Wildcards (receiver only):

        

      • MPI_ANY_SOURCE: accept a message from any sender
        • 

      • MPI_ANY_TAG: accept any tag
        • 

      • Use MPI_ANY_SOURCE when you do not know which process will finish first
        • 

      • A sender can never use a wildcard, it must name a rank and a non-negative tag
        • 

      • The textbook calls this a "push" mechanism, not a "pull"
        • 

      • There is no wildcard for the communicator
        • 

      

    • 
Finding out what a wildcard receive got:

        

      • status.MPI_SOURCE: the sender's rank
        • 

      • status.MPI_TAG: the tag
        • 

      • MPI_Get_count(&status, MPI_CHAR, &count): how many elements arrived
        • 

      • The count is not a struct member because it depends on the datatype, and computing it costs a little
        • 

      

    • 
Does a send wait?:

        

      • MPI_Recv always blocks until a matching message has arrived
        • 

      • blocking: the call does not return until it can
        • 

      • MPI_Send depends on the implementation: it may copy the message into a system buffer and return at once, or wait until the receiver is ready
        • 

      • Implementations usually pick a cutoff size, small messages are buffered and large ones block
        • 

      • When MPI_Send returns, you only know your send buffer is safe to reuse, not that the message arrived
        • 

      • Lecture 09 slide 29 calls MPI_Send synchronous, but slide 34 and the textbook say it may buffer or block, so the buffer-or-block answer is the safe one
        • 

      • MPI_Isend and MPI_Irecv are non-blocking versions, and the course does not use them
        • 

      

    • 
Message order:

        

      • MPI messages are non-overtaking: two messages from the same sender to the same receiver arrive in the order they were sent
        • 

      • Messages from different senders have no guaranteed order
        • 

      • This is why Get_input can send a, b, n with the same tag and still have them arrive in order
        • 

      

    • 
Classic pitfalls (all likely exam material):

        

      • A receive with no matching send hangs forever
        • 

      • A tag or rank mismatch makes the receive hang, or match the wrong send
        • 

      • A blocking send with no matching receive can hang
        • 

      • A buffered send with no matching receive loses the message
        • 

      • The number of sends must equal the number of receives
        • 

      • tag_mismatch.c in examples/extras/ shows the hang, and it really does hang when run
        • 

      

    • 
Checking and fixing an unsafe program:

        

      • unsafe: it only works if the system happens to buffer the messages
        • 

      • Test by replacing every MPI_Send with MPI_Ssend, which always waits until the receive has started
        • 

      • If the program still finishes, it is safe
        • 

      • Fix one way: even ranks send first and odd ranks receive first
        • 

      • Fix another way: use MPI_Sendrecv, which schedules the send and receive so they cannot deadlock
        • 

      • head_to_head.c in examples/extras/ has two ranks that each MPI_Ssend before receiving, and it hangs
        •

    4. Collective communication
    

    Lecture 10 · textbook 3.4 · about 10 minutes
    

    A collective is a call that every process in the communicator makes together. MPI decides how the data moves, usually as a tree, which beats rank 0 doing all the work itself.
    

    • 
Two kinds of communication:

        

      • point-to-point: two processes, using MPI_Send and MPI_Recv
        • 

      • collective: every process in a communicator takes part
        • 

      • Lecture 10 groups them by shape: 1-to-N (broadcast), N-to-1 (reduction), N-to-N (all-reduce)
        • 

      

    • 
Rules that differ from point-to-point (textbook 3.4.3):

        

      • Every process in the communicator must call the same collective function
        • 

      • Matching a MPI_Reduce on one process with a MPI_Recv on another is erroneous and likely hangs or crashes
        • 

      • The arguments must be compatible on every process, for example the same destination rank
        • 

      • The output argument is only used on the destination process, but every process must still pass something (NULL is fine)
        • 

      • There are no tags, calls match by communicator and by the order the calls are made
        • 

      • Never use the same variable as both input and output: MPI_Reduce(&x, &x, ...) is illegal because MPI forbids aliasing an output argument
        • 

      

    • 
Why order matters (textbook Table 3.3):

        

      • Every process calls MPI_Reduce with MPI_SUM and destination 0
        • 

      • Rank 1 reduces c first then a, the other ranks reduce a first then c
        • 

      • With a = 1 and c = 2 everywhere, the first call combines c from rank 1 with a from the others
        • 

      • So b ends up as 1 + 2 + 1 = 4 and d as 2 + 1 + 2 = 5 on three processes
        • 

      • Variable names never matter for matching, only call order does
        • 

      • reduce_order.c in examples/extras/ prints b = 4, d = 5
        • 

      

    • 
Why collectives exist (the tree idea):

        

      • A loop where rank 0 receives from everyone makes rank 0 do p - 1 receives one after another
        • 

      • A tree-structured sum lets pairs of processes combine at the same time
        • 

      • With 8 processes, ranks 1, 3, 5, 7 send to 0, 2, 4, 6 in round one
        • 

      • Then ranks 2 and 6 send to 0 and 4, and finally rank 4 sends to 0
        • 

      • That is 3 rounds, which is log2 of 8
        • 

      • MPI implementers tune the tree to the hardware, so you do not have to
        • 

      • Lecture 10's picture is an example, a real implementation may shape the tree differently
        • 

      

    • 
Try the collectives:

        

      • Pick a collective and a number of processes and see what each rank holds before and after the call
        • 

      • Move the root rank to see that it does not have to be 0
        •

        Every process contributes input_data, and the combined result lands in output_data on dest_process
        

        • 

      • With count greater than 1 it combines arrays element by element, for example adding vectors
        • 

      • The operator says how to combine: MPI_SUM, MPI_PROD, MPI_MIN, MPI_MAX, and logical or bitwise AND, OR, XOR
        • 

      • MPI_MAXLOC and MPI_MINLOC also return where the extreme value was

        Used in the trapezoid program:

        This one call replaces the whole loop of receives on rank 0
        

        • 

      • After it, total_int only holds the answer on rank 0

MPI_Allreduce:

        

      • 

        Same arguments as MPI_Reduce but with no dest_process
        


        • 

      • 

        Every process receives the combined result
        

        • 

      • The lecture calls it a butterfly reduce and draws it as a tree sum followed by the same tree run backwards
        • 

      • The textbook shows two ways to build it: reverse the tree, or have processes exchange partial results in pairs (a true butterfly)
        • 

      • Use it when every process needs the total for its next step
        • 

      • allreduce_demo.c on 4 processes: rank 0 to 3 each contribute rank + 1, and every rank prints an Allreduce total of 10
        • 

      

    • 
MPI_Bcast:

        

      • 

        Signature:
        


        • 

      • 

        The process with rank source sends, every other process receives into the same argument
        

        • 

      • So data is an input on the source and an output everywhere else
        • 

      • It is the reverse of a tree sum, so it is also fast
        • 

      • In Get_input, only rank 0 calls scanf, but all ranks call MPI_Bcast
        • 

      • The three MPI_Bcast calls sit outside the if (my_rank == 0) block on purpose
        • 

      

    • 
MPI_Scatter and MPI_Gather (lecture 10):

        

      • Scatter splits an array on one process and gives each process a different chunk
        • 

      • Gather is the reverse: it collects one chunk from every process into one array on a destination process
        • 

      • 

        Signatures:
        


        • 

      • 

        send_count in Scatter is the number of elements sent to each process, not the length of the whole array
        

        • 

      • The lecture says those arguments "describe the full array", but passing the total makes MPI abort with "Message truncated" (tested in scatter_total.c)
        • 

      • The send buffer only matters on the source, but every process supplies a receive buffer
        • 

      • Gather puts rank 0's chunk first, then rank 1's, and so on
        • 

      • scatter_gather.c: scatter 1..8, multiply by 10, gather, and rank 0 prints 10 20 30 40 50 60 70 80
        • 

      • The lecture says both will be used in the odd-even sort that comes next
        • 

      

    • 
Other collectives in the textbook summary:

        

      • MPI_Allgather: like Gather but every process gets the whole array
        • 

      • MPI_Barrier: no process returns until every process in the communicator has started the call
        • 

      • Scatter hands out the first n/p elements to process 0, the next n/p to process 1, and so on
        • 

      • That is a block distribution, and the textbook also describes cyclic (round robin) and block-cyclic
        •

    5. The trapezoidal rule
    

    Lecture 11 · textbook 3.2 to 3.4 · about 5 minutes
    

    The course's running example: estimate an integral by adding up thin trapezoids. Each rank adds up its own slice of the interval, and the partial sums are combined on rank 0.
    

    • 
The goal:

        

      • Estimate the area under a curve f(x) between x = a and x = b
        • 

      • Split the interval into n equal strips and replace each strip's curve with a straight line, which makes a trapezoid
        • 

      • The course function is f(x) = x*x, and the true area from 0 to 3 is exactly 9
        • 

      

    • 
The maths:

        

      • h is the width of every trapezoid: h = (b - a) / n
        • 

      • Area of one trapezoid: (h / 2) * (f(x_i) + f(x_i+1))
        • 

      • Whole estimate: h * [ f(a)/2 + f(x_1) + ... + f(x_n-1) + f(b)/2 ]
        • 

      • The middle points are counted twice (once for each neighbouring trapezoid), and the two end points once, which is why those two are halved
        • 

      • On a convex curve each trapezoid overestimates, on a concave curve it underestimates
        • 

      • As the trapezoids get narrower, the errors average out
        • 

      

    • 
The serial code (this is Trap in every course version):


        • 

      • Line 149: start with the two halved end points
        • 

      • Lines 150 to 153: add f(x) for each middle point
        • 

      • Line 154: multiply by h once at the end
        • 

      

    • 
Designing the parallel version (lecture 11 follows these four steps):

        

      • Partition: give each process one slice of the interval
        • 

      • Communicate: everyone needs a, b, n, and the partial results must be added together
        • 

      • Aggregate: rank 0 also does the input, the summing and the output
        • 

      • Map: rank 0 sums, other ranks compute a slice and send the result to rank 0
        • 

      

    • 
Each rank's slice:

        

      • h = (b-a)/n is the same on every rank
        • 

      • local_n = n/comm_sz is the number of trapezoids per rank
        • 

      • local_a = a + my_rank*local_n*h is where this rank's slice starts
        • 

      • local_b = local_a + local_n*h is where it ends
        • 

      • Each rank calls Trap(local_a, local_b, local_n, h) on its own slice
        • 

      • Example: a = 0, b = 3, n = 1024 on 4 ranks gives local_n = 256, so rank 2 covers 1.5 to 2.25
        • 

      • The Trapezoid trace lets you try other numbers
        • 

      

    • 
The assumption that is easy to forget:

        

      • The code assumes n divides evenly by comm_sz
        • 

      • Integer division truncates, so leftover trapezoids are never computed
        • 

      • With n = 1024 on 3 ranks, local_n is 341 and only 1023 trapezoids are covered
        • 

      • The program then prints 8.9737 instead of about 9.0000 (checked by running it)
        • 

      • The slides say they assume even division to keep examples short
        • 

      • Textbook exercise 3.2 asks you to fix it
        • 

      

    • 
The three versions in the course:

        

      • Program 3.2, the textbook's first version: a = 0, b = 3, n = 1024 hard-coded, results summed with a loop of Send and Recv
        • 

      • mpi_trap2, shipped here as mpi_SendRec.c: keyboard input sent to each rank with MPI_Send, results summed with a loop of MPI_Recv
        • 

      • mpi_trap3, shipped here as mpi_Bcast.c: MPI_Bcast for the input and MPI_Reduce for the sum
        • 

      • mpi_trap4 uses MPI derived datatypes, which lecture 11 says have not been covered
        • 

      

    • 
What changes between versions 2 and 3:

        

      • Input: three MPI_Send calls per other rank become three MPI_Bcast calls
        • 

      • Sum: an if/else with a loop becomes one MPI_Reduce
        • 

      • The maths and the Trap function do not change
        • 

      • Result for a = 0, b = 3, n = 1024 on 4 ranks is 9.000004291534424e+00 in both
        • 

      • It is a little above 9 because x squared is convex, so every trapezoid overestimates
        •

    6. Odd-even sort with MPI
    

    Lecture 12 · about 10 minutes
    

    The odd-even sort from the pthreads unit, with each block on its own rank. Getting a partner's block now takes a message, and the obvious send-then-receive version can deadlock.
    

    • 
What lecture 12 is about:

        

      • The same odd-even transposition sort from the pthreads unit, rewritten for distributed memory
        • 

      • Same decomposition, same phases. The one new question: how does a rank get its partner's block when it cannot read that memory?
        • 

      • Answer: it receives it in an MPI message, so communication is no longer free
        • 

      • The course file mpi_odd_even.c is not in the project files yet, so this section uses the code shown on the slides
        • 

      

    • 
The serial algorithm (review):

        

      • odd-even transposition sort: a bubble sort variant split into phases
        • 

      • even phase: compare-swap the pairs (a[0], a[1]), (a[2], a[3]), ...
        • 

      • odd phase: compare-swap the pairs (a[1], a[2]), (a[3], a[4]), ...
        • 

      • compare-swap: if the left value is bigger, swap the two
        • 

      • A list of n elements is sorted after at most n phases
        • 

      • Slide example: 5 9 4 3, then 5 9 3 4, then 5 3 9 4, then 3 5 4 9, then 3 4 5 9 (4 phases)
        • 

      

    • 
Foster's methodology, one step at a time:

        

      • Partitioning: the smallest task is one compare-swap on a neighbouring pair
        • 

      • Inside one phase the pairs do not overlap, so all compare-swaps can run at once
        • 

      • Across phases it is serial: phase j must finish before phase j + 1 starts
        • 

      • Communication: each compare-swap needs both values of its pair
        • 

      • In pthreads that was just a read of shared memory
        • 

      • In MPI it is a real message: send your block, receive your partner's block
        • 

      • This is the step that cannot be copied from the pthreads version
        • 

      • Agglomeration: group n/p contiguous elements into one block per rank
        • 

      • Inside a block, sorting is a local qsort()
        • 

      • Between blocks, a compare-swap of two numbers becomes a compare-split of two sorted blocks
        • 

      • compare-split: merge the two sorted blocks, the lower rank keeps the low half and the higher rank keeps the high half
        • 

      • Mapping: block r goes to rank r, so neighbouring blocks stay on neighbouring ranks
        • 

      • The example code requires global_n to divide evenly by p
        • 

      

    •

      • It depends on your rank's parity and the phase's parity

The exchange, from the slides:


        • 

      • local_A is my block, temp_B receives the partner's block, temp_C is scratch space for the merge
        • 

      • One call sends and receives at the same time, in both directions
        • 

      • In an even phase, odd ranks are the higher member of their pair, so they keep the high half
        • 

      • The lecture renamed the book's Merge_low and Merge_high to Merge_keep_low and Merge_keep_high
        • 

      • Why there are no barriers
          

        • In pthreads, a fast thread could overwrite its block while a slow partner was still reading it, so each phase needed two barriers that every thread had to hit
          • 

        • In MPI each rank's memory is private, so there is nothing for a fast rank to overwrite
          • 

        • MPI_Sendrecv only synchronizes the two ranks in the pair. It is not a group-wide wait
          • 

        • An idle rank makes no call at all and moves straight on
          • 

        • Synchronization is a side effect of the communication call
          • 

      

    • 
Phases can get out of step:

        

      • Nothing forces all ranks to be in the same phase
        • 

      • Example: rank 3 finishes phase 0, has no partner in phase 1, starts phase 2 and blocks sending to rank 2
        • 

      • Meanwhile rank 2 may still be finishing its phase 0 merge
        • 

      • That is correct: rank 3 simply waits inside MPI_Sendrecv until rank 2 arrives
        • 

      

    • 
Why not plain MPI_Send then MPI_Recv?:

        

      • If both ranks in a pair run MPI_Send then MPI_Recv, it often works
        • 

      • Whether MPI_Send blocks is up to the implementation, and usually depends on message size
        • 

      • Small messages are buffered, so the send returns before any receive is posted
        • 

      • Large messages are not buffered, so each send waits for a receive that never starts: a deadlock
        • 

      • So small test data passes every time and large data hangs. The bug is latent, not absent
        • 

      • deadlock: two or more processes each waiting on the other, so none can continue
        • 

      

    • 
Forcing the deadlock with MPI_Ssend:


        • 

      • MPI_Ssend never returns until the matching receive has started
        • 

      • Both ranks block in MPI_Ssend, so neither reaches its MPI_Recv
        • 

      • Changing only the even-phase branch is enough: every pair deadlocks in phase 0
        • 

      • make run-lock runs this version. Each rank prints "sending to ... and waiting", then it hangs
        • 

      • See Hangs and mix-ups for the same pattern with two ranks (head_to_head.c)
        • 

      

    •

      • Build: mpicc -g -Wall -o mpi_odd_even mpi_odd_even.c
        • 

      • Run: mpiexec -n <p> mpi_odd_even <g|i> <global_n>
        • 

      • g generates a random list on each rank, i makes rank 0 read the list from stdin and scatter it
        • 

      • Rank 0 gathers and prints the sorted list. The lecture moved the hidden MPI_Gather out of Print_global_list into main
        • 

      • mpi_odd_even_trace.c builds with -DTRACE, -DSLOW_RANK=k and -DSTEP to show each send, receive and keep
        •

    7. Heat distribution with MPI
    

    Lecture 13 · about 15 minutes
    

    The heat plate from the pthreads unit, split into row bands, one per rank. Each rank keeps copies of the rows just outside its band and refreshes them with a message every iteration.
    

    • 
What lecture 13 is about:

        

      • The heat diffusion case study from the pthreads unit, rewritten for distributed memory
        • 

      • A rank only sees its own memory, so reading a neighbour's row now means receiving a message
        • 

      • Everything else (the plate, the averaging rule, the stopping rule) is the same
        • 

      

    • 
The problem (review):

        

      • A square plate, cold on all four edges, with a hot block held fixed in the centre
        • 

      • Each interior cell's next value is the average of its 4 neighbours (up, down, left, right) from the previous step
        • 

      • fixed cells: the cold edges and the hot block. They never update
        • 

      • Repeat until the largest change anywhere on the plate drops below EPSILON
        • 

      • Orientation used in the lecture: row 0 is the top, row N - 1 the bottom, so row i + 1 is "down"
        • 

      

    • 
The pthreads version it replaces:

        

      • Each thread owns a contiguous band of rows and reads any row of the shared grid directly
        • 

      • Two barriers per iteration: after everyone writes, and after thread 0 computes the global max, swaps and decides
        • 

      • Hazard 1: a thread reading a neighbour's row while it is being written
        • 

      • Hazard 2: threads racing past thread 0's stop decision
        • 

      • Keep both in mind, MPI removes them in a different way
        • 

      

    • 
Foster's methodology again:

        

      • Partitioning: unchanged. One cell's update is the smallest task. Within an iteration all cells are independent, across iterations they are strictly ordered
        • 

      • Communication: the step that changes. A rank needs the row just above and just below its band, and another rank owns those rows
        • 

      • So every rank, every iteration: two rows in, two rows out
        • 

      • Agglomeration: still one contiguous band of rows per rank, but now the band also stores copies of the two rows outside it
        • 

      • Mapping: same arithmetic as pthreads, plus a new job: the tables must let rank 0 put the whole grid back together for output
        • 

      

    • 
Ghost rows:

        

      • ghost row (also called a halo row): a local copy of a row owned by a neighbouring rank
        • 

      • A rank with my_rows rows allocates (my_rows + 2) x N doubles, the 2 extra rows are the ghosts
        • 

      • The rank stores and reads its ghost rows but never computes them
        • 

      • halo exchange: refreshing the ghost rows from the neighbours once per iteration, before computing
        • 

      

    •

        •

Exchange topology:

        

      • Each interior rank does two exchanges: one with the rank above, one with the rank below
        • 

      • Rank r's down-exchange is matched by rank r + 1's up-exchange
        • 

      • Rank 0 has no rank above, the last rank has no rank below
        • 

      

    • 
The halo exchange, two calls per iteration:


        • 

      • IDX(i, j) is i * N + j, so &cur[IDX(1, 0)] is the start of local row 1
        • 

      • Example with 4 ranks: rank 1's local row 1 (global 5) lands in rank 0's local row 5, its bottom ghost
        • 

      • And rank 0's local row 4 (global 4) lands in rank 1's local row 0, its top ghost
        • 

      • MPI_Sendrecv posts its receive as part of the call, so no rank is stuck mid-send
        • 

      • It does not return until the incoming row has arrived, so a rank cannot compute with a half-updated ghost
        •

The ends: MPI_PROC_NULL:


        • 

      • MPI_PROC_NULL: MPI's name for "nobody". A send or receive with it finishes at once and does nothing
        • 

      • Rank 0's top ghost and the last rank's bottom ghost are left alone, and they already hold the cold edge
        • 

      • So every rank makes the same two calls, with no if for the boundary ranks
        • 

      

    • 
Convergence check: one call:


        • 

      • Each rank finds the largest change in its own band, MPI_MAX combines them, and every rank receives the result
        • 

      • No rank leaves the call until every rank has entered it, so it also acts as the barrier
        • 

      • Every rank then tests global_max < EPSILON || iteration >= MAX_ITERS - 1 on the same number, so all stop together
        • 

      • Barrier, thread 0's reduction loop, barrier: three pthreads constructs become one line
        • 

      

    •

        •

        • 

      • MPI_Gatherv: "v" for varying. It takes a count per rank and a displacement per rank saying where that rank's data lands

The loop, end to end:

        

      • Step 1: Halo exchange: two MPI_Sendrecv calls refresh both ghost rows of cur
        • 

      • Step 2: Compute: for each owned row, convert to the global row, copy fixed cells, average the rest into next, track local_max
        • 

      • Step 3: MPI_Allreduce with MPI_MAX gives every rank global_max
        • 

      • Step 4: Swap cur and next
        • 

      • Step 5: Every FRAME_STRIDE iterations, MPI_Gatherv to rank 0, and rank 0 writes the frame
        • 

      • Step 6: Every rank decides for itself whether to stop, on identical data
        •

Worked example:


      • 16 x 16 grid, 6 x 6 hot block, 4 ranks, iteration 10
          

        • The full grid exists only in our heads, and on rank 0 when a frame is written. No rank holds it
          • 

        • Rank 2 owns global rows 9 to 11. Its top ghost copies global row 8 (rank 1) and its bottom ghost copies global row 12 (rank 3)
          • 

        • At the start of iteration 10 both ghosts still hold last iteration's copies, which are now stale
          • 

        • After the exchange the ghosts are fresh and the three owned rows are untouched: the exchange only writes ghosts
          • 

        • Only now may rank 2 compute, which is why the exchange comes first in the loop
          • 

      • Why there are no barriers
          

        • Hazard 1 (reading a row mid-write) is gone: data only crosses a rank boundary when it is sent, and MPI_Sendrecv does not return until it has landed
          • 

        • Hazard 2 (racing past the stop decision) is gone: MPI_Allreduce releases nobody until everyone has arrived, and gives them all the same number
          • 

        • MPI does not need less synchronization. The synchronization is inside the calls that move the data
          • 

        • In pthreads the data moved for free and you paid separately in barriers. In MPI you pay once, in the call that does both
          • 

    • 
Summary of what changed from pthreads:

        

      • A free read became a message: two ghost rows per rank, two MPI_Sendrecv calls per iteration
        • 

      • An implicit mapping became an explicit one: someone has to know every rank's slice to reassemble the grid
        • 

      • Barrier, reduction, barrier became one MPI_Allreduce
        • 

      • Two hazards disappeared, because process isolation removed both the free read and the race
        • 

      • The lecture's moral: the memory model decides which problems you have and how you solve them
        •

        •

        •

        •

Timing the program:

        

      • Four MPI_Wtime accumulators per rank: compute, comm (the two Sendrecvs), reduce (the Allreduce), output (Gatherv and file write)

    8. Hardware and performance
    

    Lecture 14 · textbook 2.3, 2.6.1 to 2.6.2 · about 10 minutes
    

    A map of parallel hardware, then the numbers that say whether parallelism paid off: speedup, efficiency, and Amdahl's law, which caps speedup by the part that stays serial.
    

    • 
What lecture 14 is about:

        

      • Part 1: a map of parallel hardware, so you can name what kind of machine you are on
        • 

      • Part 2: speedup, efficiency, overhead and Amdahl's law. This is where the exam calculations come from
        • 

      • Textbook: section 2.3 (part 1) and sections 2.6.1 to 2.6.2 (part 2)
        • 

      

    • 
Flynn's taxonomy:

        

      • Classifies a machine by how many instruction streams and data streams it runs at once
        • 

      • SISD (single instruction, single data): the serial von Neumann machine, one core
        • 

      • SIMD (single instruction, multiple data): one control unit drives many ALUs, all doing the same instruction on different data
        • 

      • MISD (multiple instruction, single data): almost no real systems
        • 

      • MIMD (multiple instruction, multiple data): independent cores, each with its own ALU, running asynchronously at their own pace
        • 

      • ALU (arithmetic logic unit): the part of a core that does the arithmetic
        • 

      

    • 
SIMD in more detail:

        

      • With m ALUs, arithmetic can run up to m times faster
        • 

      • Traditional SIMD ALUs are synchronized and tied to the controller, they cannot store their own instructions
        • 

      • Good for simple loops over large arrays (data parallelism), not much else
        • 

      • vector processor: an example of SIMD. Vector registers hold 4 to 256 elements, and one operation applies to all of them
        • 

      • Vector pros: fast and easy, compilers vectorize loops well, high memory bandwidth because every loaded element is used
        • 

      • Vector cons: poor with irregular data structures (anything that is not an array), and hard to scale since longer vectors stop helping
        • 

      • Lecture 15 adds SIMT, the GPU's version of this idea
        • 

      

    • 
MIMD comes in two memory models:

        

      • shared memory: all cores see one memory over an interconnect (pthreads)
        • 

      • distributed memory: each core has its own memory, and they talk over a network (MPI)
        • 

      

    • 
Shared memory: UMA and NUMA:

        

      • UMA (uniform memory access): one big memory, every core has the same access time. Easier to program
        • 

      • NUMA (nonuniform memory access): each chip has its own local memory. Local access is fast, reaching another chip's memory is slower
        • 

      • NUMA exists because it allows much more total memory than UMA
        • 

      

    • 
Distributed memory systems:

        

      • cluster: a collection of computers (nodes) on a commodity network such as Ethernet
        • 

      • Each node is usually a shared-memory machine, so a cluster is a hybrid system
        • 

      • grid: many clusters spread over a large geographic area, often heterogeneous (different hardware and operating systems)
        • 

      

    • 
Shared-memory interconnects:

        

      • bus: one set of shared wires. Cheap and flexible, but more processors means more waiting for memory
        • 

      • crossbar switch: switches pick one of many paths, so different CPUs can reach different memory modules at the same time
        • 

      • The only crossbar conflict is two processors wanting the same memory module
        • 

      • A crossbar is faster than a bus but expensive
        •

Speedup:

        

      • speedup: S = T_serial / T_parallel

        •

        • 

      • It rarely happens. Thread management, critical sections, mutex calls, network I/O and file I/O all slow a parallel program
        • 

      • These overheads grow as threads or processes are added
        •

      • efficiency: E = S / p = T_serial / (p x T_parallel)
        •

    9. GPGPU and Warp
    

    Lecture 15 · about 15 minutes
    

    A GPU has thousands of simple cores that run the same instruction in lockstep. You hand it a stream of data and a small kernel function, and it runs the kernel once per element.
    

    • 
What lecture 15 is about:

        

      • Why GPUs exist, how their hardware differs from a CPU, and the stream programming model
        • 

      • How to write a first GPU kernel with Nvidia Warp
        • 

      • GPU (graphics processing unit): a processor with thousands of simple cores, built for graphics
        • 

      • GPGPU (general-purpose computing on GPUs): using that hardware for other work
        • 

      

    • 
Why GPUs exist:

        

      • A game at 1920 x 1080 has about 2 million pixels per frame
        • 

      • At 60 frames per second that is about 120 million pixel colours per second
        • 

      • Each pixel needs several matrix and vector operations, and each of those takes dozens of CPU instructions
        • 

      • No CPU keeps up with that for a modern game, so dedicated hardware was built
        • 

      • 3D rendering is all coordinates and vectors (3 or 4 components) and transformation matrices: rotation, translation, scaling, projection
        • 

      • The same operation on huge amounts of data: it "feels a bit SIMD-y"
        • 

      

    • 
What GPUs give up:

        

      • They are optimized for one thing: basic matrix and vector arithmetic
        • 

      • They skip complex branch logic and cache management, and spend most transistors on processing units
        • 

      • CPUs have about 2 to 96 cores (over 250 at the top end). GPUs have hundreds to thousands, over 10,000 on high-end cards
        • 

      • More cores means more pixels at once, so higher resolution or higher frame rate
        • 

      

    • 
What GPGPU is used for:

        

      • Physics simulations: objects are points (vectors), forces are vectors and matrices
        • 

      • Machine learning: training adjusts network weights, which can be written as vector operations. GPGPU largely enabled the ML boom of the last 15 to 20 years
        • 

      • Image processing: pixels are points, and many image operations are matrices (lectures 16 and 17)
        • 

      • Also robotics, audio and video, science and finance
        • 

      

    • 
The stream programming model:

        

      • stream: an ordered set of data of one type, expected to have thousands of elements or more
        • 

      • It can be simple (floats) or complex (points, triangles, matrices)
        • 

      • Operations on streams: copy them, index into them with another stream, and run kernels on them
        • 

      • kernel: a small function applied to entire streams. It takes one or more streams in and produces one or more streams out
        • 

      • The word comes from mathematics, and image processing uses it for a filter matrix (lecture 16)
        • 

      

    • 
Kinds of kernel operation:

        

      • map: evaluate a function on every element, the most common use
        • 

      • expansion: more than one output element per input element
        • 

      • reduction: several elements combine into one output element
        • 

      • filter: only some input elements are output
        • 

      • Each step of a rendering pipeline can be one or more kernels, and several can be fused into one
        • 

      

    • 
The rule that makes kernels parallel:

        

      • A kernel's outputs depend only on its inputs
        • 

      • Inside a kernel you may read any element of the input arrays and write one output
        • 

      • Your output may not depend on another thread's output
        • 

      • So everything a kernel needs is known when it is written, and each element can run on its own core
        • 

      • This is why a kernel that reads like a serial loop body can run on data-parallel hardware
        • 

      

    • 
The GPGPU pattern:

        

      • Arrange the problem so the input is a stream
        • 

      • Write one or more kernels that operate on it. Several kernels run in sequence, only one is applied to a stream at a time
        • 

      • Load the data and the kernel, and run
        • 

      

    • 
SIMD against SIMT:

        

      • SIMD: one thread with very wide registers. One fetch and decode, one register file, several execution lanes
        •

        • 

      • Multi-core CPU: multiple independent threads. x86 SSE vector unit: one thread with a wide data path. GPU: multiple lockstep threads

    • GPU hardware hierarchy:
        

      • shading unit: a small, simple unit that runs floating-point operations. Nvidia calls them CUDA cores
        • 

      • A shading unit often runs more than one SIMT thread
        • 

      • compute unit: a group of shading units, usually dozens and up to 128 or more
        • 

      • A GPU is many compute units
        • 

      • Branch divergence
          

        • Threads in a lockstep group share one instruction stream
          • 

        • If they take different branches of an if, the group runs both paths and masks off the threads that should not be active
          • 

        • So divergent code costs the time of both branches added together
          • 

        • Best practice: one flat data buffer, one kernel, uniform work on every element
          •

Homogeneous against heterogeneous computing:

        

      • homogeneous: every execution unit is the same type. Pthreads and MPI both run on CPU cores
        • 

      • MPI nodes can differ a little, but the code must run on all of them: Intel with AMD is fine (both x86), Intel with ARM is not
        • 

      • heterogeneous: different kinds of processor work together. GPGPU is the example
        • 

      • host: the CPU side. It starts the program, loads the data stream and the compiled kernels, sends both to the GPU, runs the kernels and copies the results back
        •

The new cost: copying to the GPU:

        

      • Once data is on the GPU, kernels get direct memory access, like threads (and data races are possible)
        • 

      • But on most systems the CPU and GPU have separate memories, like distributed memory
        • 

      • Moving data to the GPU is a copy over the bus, and it is expensive
        • 

      • For small problems the copy can dominate, so a naive GPU port can be slower than the CPU version
        • 

      

    • 
GPGPU libraries:

        

      • CUDA: Nvidia's proprietary platform. Only runs on Nvidia GPUs, and is the industry favourite
        • 

      • OpenCL: an open standard that runs on many platforms. Used where Nvidia hardware is not guaranteed, but declining
        • 

      • In both, the CPU code is C and the kernel is written in a separate kernel language
        • 

      • Nvidia Warp: the course's choice. Free, open source, and both the CPU code and the kernel are Python

      • Warp converts the Python to C++ and CUDA and compiles it at run time (just-in-time, JIT)

    10. Image processing basics
    

    Lecture 16 · about 10 minutes
    

    An image is a matrix of numbers. Most filters compute each new pixel as a weighted sum of its neighbours, which is called convolution, and the image borders need special handling.
    

    • 
What lecture 16 is about:

        

      • The image-processing ideas needed for A3: how images are stored, neighbourhoods, convolution and kernels, and what to do at the borders
        • 

      • Images are loaded with PIL (the Python Imaging Library) as a matrix of pixel values, which can be passed to Warp as a stream
        • 

      

    • 
How images are stored:

        

      • greyscale image: one matrix of intensities, one number per pixel
        • 

      • colour image: three matrices (red, green, blue), or one matrix of 3-value vectors
        • 

      • RGBA: adds a fourth channel, alpha, for transparency
        • 

      • The examples use greyscale because one matrix is simpler
        • 

      • To process a colour image, run the same algorithm on each channel separately
        • 

      

    • 
Filtering:

        

      • filtering: removing "impurities" from an image, such as noise. Also called image restoration or enhancement
        • 

      • It covers noise removal, sharpening and contrast enhancement
        • 

      • The word is also used loosely for effects such as a sepia tone
        • 

      

    • 
Neighbourhoods:

        

      • A pixel's new value is computed from its old value and the pixels around it, its neighbourhood
        • 

      • 4-neighbours of (x, y): (x+1, y), (x-1, y), (x, y+1), (x, y-1)
        • 

      • 8-neighbours: the 4-neighbours plus the 4 diagonals (x+1, y+1), (x+1, y-1), (x-1, y+1), (x-1, y-1)
        • 

      • On the border of the image, some neighbours fall outside it
        • 

      • 

        The 3 x 3 neighbourhood of (x, y):
        


        • 

      

    • 
Convolution:

        

      • convolution: the new value at a pixel is a weighted sum of the intensities in the neighbourhood around it
        • 

      • The weights come from a convolution kernel, also called a mask or filter: a small matrix the same size as the neighbourhood
        • 

      • A neighbourhood centred on a pixel must have odd dimensions: 3 x 3, 5 x 5, ...
        • 

      • Formula for a 3 x 3 kernel: g(x, y) = sum over i, j in -1..1 of w(i, j) * f(x + i, y + j)
        • 

      • f is the input image, g the output image, w the kernel
        • 

      

    • 
The convolution process, step by step:

        

      • Step 1: Place the centre of the kernel over a pixel P in the input image
        • 

      • Step 2: Multiply each pixel in the k x k neighbourhood by the kernel coefficient on top of it
        • 

      • Step 3: Add up all the products
        • 

      • Step 4: Write the (normalized) sum into position P of the output image
        • 

      • Always read from the input and write to a separate output, so later pixels still see the original values
        • 

      

    • 
Worked example:


      • 3 x 3 mean filter on the lecture's neighbourhood
          

        • Kernel: every coefficient is 1/9
          •

        • 1835 / 9 = 203.9, which rounds to 204
          • 

        • The centre pixel 249 becomes 204 in the output
          • 

    • 
Kinds of kernel:

        

      • omnidirectional: responds the same whichever direction the intensity changes in
        • 

      • uniform: all coefficients have the same weight (the mean filter)
        • 

      • nonuniform: coefficients have different weights (pyramid, cone, Gaussian)
        • 

      

    • 
Normalization:

        

      • Kernels are usually normalized: each coefficient is divided by the sum of all coefficients
        • 

      • The factor is often written outside the matrix, for example 1/9 in front of a matrix of 1s
        • 

      • In code the coefficients are often already divided
        • 

      • Why: a region of constant intensity should keep the same value after filtering
        • 

      • And it avoids bias: the original and filtered images should have the same total brightness
        • 

      • Sharpening kernels whose coefficients sum to 0 are the exception (lecture 17)
        •

Ways to handle the border:

        

      • Copy the input pixels: where convolution is impossible, copy the input value. The output has an unprocessed frame
        • 

      • Truncate the image: drop those pixels. The output is smaller than and offset from the input
        • 

      • Truncate the kernel: use a smaller, modified kernel at edges and corners. Correct, but adds a lot of complexity
        • 

      • Reflected indexing: if x + i falls outside the image, reflect it back inside, as if the image were mirrored at its edges. The lecture calls this the most useful option
        • 

      • Circular indexing: pretend the image repeats forever in every direction, so falling off the right edge wraps to the left. Rarely used in image processing
        •

          •

          • 

        • So the row 10 20 30 40 50 is read as 20 | 10 20 30 40 50 | 40 at the edges
          • 

        • Some libraries reflect to index 0 instead (repeating the edge pixel). Check which one your assignment asks for
          • 

    • 
Connecting this to GPGPU (lecture 15):

        

      • Each output pixel depends only on input pixels, never on other output pixels
        • 

      • That is exactly the kernel rule, so one thread per output pixel works
        • 

      • Each thread finds its (x, y), loops over the k x k neighbourhood of the input, and writes one output value
        • 

      • Writing into the input image instead would break the rule, because neighbouring threads would read half-updated values
        • 

      • The border handling is a branch, so pixels near the edge can cause some divergence, but only along a thin frame
        •

    11. Sharpening and smoothing
    

    Lecture 17 · about 10 minutes
    

    Smoothing filters average neighbours to remove noise but blur edges. Sharpening does the opposite and makes noise worse. The median filter removes isolated spikes and keeps edges.
    

    • 
What lecture 17 is about:

        

      • The fundamental filters: sharpening (high-pass, unsharp masking) and smoothing (mean, Gaussian, median)
        • 

      • All but the median are convolutions with the kernels from lecture 16
        • 

      

    • 
Why images need fixing:

        

      • blur: details are smoothed out. Causes: out-of-focus optics, lens aberrations, atmospheric turbulence, camera motion during long exposures
        • 

      • noise: artifacts added when the image is captured
        • 

      • Noise comes from variation in photon counts and from the sensor itself (read noise)
        • 

      • Sensor noise gets worse as temperature rises, and as sensitivity is raised in low light
        • 

      

    • 
Low-pass and high-pass:

        

      • "Low" and "high" refer to spatial frequency: how quickly intensity changes across the image
        • 

      • low-pass filter (LPF): lets slow changes through and removes quick ones. Smooths, removes noise. Also called a "high-cut" filter
        • 

      • high-pass filter (HPF): the image minus its low-pass version. Keeps sudden changes like edges, suppresses gradual ones
        • 

      • high-boost filter: part of the high-pass result added back to the image
        • 

      • Quick, closely spaced changes can be unwanted (noise) or wanted (fine detail). A filter cannot tell them apart
        • 

      

    • 
Simple sharpening:

        

      • A high-pass kernel mixes positive and negative values
        • 

      • 

        Omnidirectional version: positive at the centre, negative around it, coefficients summing to 0
        


        • 

      

    • 
Why the sum is 0:

        

      • Over a flat region every pixel is equal, so 8v - 8v = 0
        • 

      • Over a slow change the result is small
        • 

      • Over a sharp change the result is large
        • 

      • Example: three columns of 10, 10, 50 give -120. Columns 10, 50, 50 give +120. Flat 50 everywhere gives 0
        • 

      • So the output is an edge map. It is not normalized like a smoothing kernel, because its sum is 0
        • 

      

    • 
Caveats of sharpening:

        

      • Noise is high-frequency, so sharpening makes noise more visible
        • 

      • In practice, remove noise first, then sharpen
        • 

      

    • 
Unsharp masking:

        

      • Introduced by Schreiber in 1970 to improve newspaper wirephotos, based on a darkroom technique of sandwiching a blurred positive with the negative
        • 

      • Idea: subtract a blurred copy from the image, which removes the low frequencies and leaves the edges
        • 

      • Unlike the single-kernel filters, it is a multi-step method
        • 

      • Step 1, edge image: g(x, y) = f(x, y) - S(f(x, y)), where S(f) is a blurred version of f
        • 

      • Step 2, add it back: f_UM(x, y) = f(x, y) + k * g(x, y)
        • 

      • k is a scaling constant. Reasonable values are 0.2 to 0.7, larger means sharper
        • 

      • With k > 1 it is called a high-boost filter
        • 

      

    • 
Unsharp masking with numbers:


      • A 1D edge, blurred with a 3-wide mean, k = 0.5
          

        • Input row: 10 10 10 10 50 50 50 50
          • 

        • Blur (edges repeated): 10 10 10 23.3 36.7 50 50 50
          • 

        • Edge image g = input - blur: 0 0 0 -13.3 13.3 0 0 0
          • 

        • Result f + 0.5 g: 10 10 10 3.3 56.7 50 50 50
          • 

        • The dark side of the edge dips below 10 and the bright side rises above 50: that is overshoot
          • 

    • 
Limits of unsharp masking:

        

      • noise sensitivity: it emphasizes high frequencies, and noise is high frequency
        • 

      • overshoot: wide, abrupt brightness changes get an exaggerated rim
        • 

      • It makes an edge steeper by making it taller. Many sharpening methods share this trait
        • 

      • In the lecture's example, the square elements look brighter than in the original
        • 

      

    • 
Denoising in general:

        

      • Noise filters are smoothing (low-pass) filters
        • 

      • Two families: mean-based (mean, Gaussian) and order-statistic (median and other rank filters)
        • 

      

    • 
Mean filter (box filter):

        

      • Replace each pixel with the average of its neighbourhood. Also called sliding mean or box filter
        • 

      • 3 x 3: sum the 9 values and divide by 9. 5 x 5: sum 25 and divide by 25
        • 

      • It reduces noise because noise is sharp transitions, but edges are sharp transitions too, so edges blur
        • 

      • It is the opposite of sharpening
        • 

      • Larger kernels, or applying a small kernel repeatedly, smooth more
        • 

      • Effective against Gaussian noise
        • 

      

    • 
Gaussian filter:

        

      • A smoothing filter with a nonuniform kernel built from a 2D Gaussian function
        • 

      • w(i, j) = e^(-(i^2 + j^2) / (2 sigma^2)) for i, j from -[3 sigma] to [3 sigma]
        • 

      • [3 sigma] means the integer part of 3 sigma. Beyond 3 sigma the weights are negligible
        • 

      • Coefficients shrink with distance from the centre, so central pixels count more than the edges of the neighbourhood
        • 

      • Larger sigma: a wider spread, more blur, and a bigger kernel
        • 

      • isotropic (rotationally symmetric): no direction is smoothed more than another
        • 

      • With sigma^2 = 1 the kernel is 7 x 7. Normalized and multiplied by 1000 its centre row is 2 22 97 159 97 22 2, and its centre is 159
        • 

      • Other common values: sigma^2 = 2/3 and sigma^2 = 2
        • 

      • Compared with a mean filter of similar size, edges blur less, because far-away pixels count less
        • 

      • Exam trap
          

        • The median filter is not a convolution. No set of weights picks the middle value for every neighbourhood, so it has no kernel matrix
          • 

      

    • 
Rank (order-statistic) filters:

        

      • Non-linear filters: list the neighbourhood's values, sort them, and pick the value at a chosen position
        • 

      • Positions include the median, lower quartile and upper quartile
        • 

      • Because sorting is not a weighted sum, a rank filter is not a convolution and has no kernel matrix
        • 

      

    • 
Median filter:

        

      • Replace the pixel with the middle value of its sorted neighbourhood
        • 

      • Lecture example (5 x 5): the sorted 25 values are 9 11 21 23 23 23 27 34 45 46 87 90 98 100 103 104 104 104 105 105 106 108 109 110 112
        • 

      • The 13th value is the median: 98
        • 

      • Used to remove impulse noise (salt and pepper: isolated very bright or very dark pixels)
        • 

      • It works when the noisy pixels are less than half the neighbourhood, because the median then comes from the clean majority
        • 

      • Example: a 3 x 3 of eight 10s and one 255. The mean is 37.2 (the spike smears out), the median is 10 (the spike is gone)
        • 

      

    • 
Median filter strengths and weaknesses:

        

      • It does not compress the brightness range inside the neighbourhood, so sharp and straight edges survive
        • 

      • It is non-specific: any structure smaller than half the neighbourhood is removed, real or noise
        • 

      • So thin lines and small objects disappear too
        • 

      • Repeated application causes posterization: flat patches of colour with hard boundaries
        •

        •
